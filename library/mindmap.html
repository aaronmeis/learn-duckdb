This mind map was drafted from the Mode B interview. Edit freely, then check Progress Log.

DuckDB

  • Day outcome: By the end of the day, explain DuckDB from zero and sketch one local analytics query you could defend. The sketch names the storage layout, the execution model, and when DuckDB beats Postgres, SQLite, Polars, or Spark. Success is a short written explanation plus that sketch, with one named failure mode.
  • Depth: Working fluency across the engine, not a survey of every SQL function and not a single-subsystem deep dive. Enough to sketch a scan-join-aggregate and say why the engine runs it that way. A later day can go deep on one slice (vectorized execution, or the storage format).
  • Prior knowledge: Assume zero. Define a table, a query, a join, OLTP versus OLAP, and row storage versus column storage before any DuckDB-specific term. Do not assume the CLI, Parquet, or EXPLAIN.
  • Boundaries: Must include: what DuckDB is (in-process SQL database), row versus column storage, vectorized execution, morsel-driven parallelism, the single-file database, reading Parquet and CSV, EXPLAIN at a sketch level, extensions in outline, and when not to use DuckDB.

Out of scope: a production deploy, building a DuckDB extension in C++, distributed DuckDB clusters, and multi-week academy depth. No local lab is required today. - Core concepts - A table, a query, and a join, defined without DuckDB - OLTP (many small row updates) versus OLAP (few large scans and aggregates) - Row storage versus column storage - DuckDB as an in-process SQL database, not a server you connect to - A single database file, or memory only - Reading CSV and Parquet without loading them into a server first - What EXPLAIN is for, at sketch level - Mental models - Columnar layout: one query touches a few columns, so it reads those columns only - Vectorized execution: the engine processes a batch of values per operator, not one row at a time - Morsel-driven parallelism: threads take chunks of the same pipeline - Out of core: the working set can exceed RAM and spill - Replacement scan: a data frame or file can stand in for a table name - Comparison set: Postgres, SQLite, Polars, Spark. Each wins a different job. - Active practice targets - On paper, define the five words above in your own sentences - Sketch a scan, join, and aggregate over a Parquet file of events and a small dimension table - Annotate the sketch with which steps are columnar and which step needs a join - Read one EXPLAIN tree from the docs and label scan, join, and aggregate - Teach-back angle - Five minutes to someone who knows Excel and has heard of SQLite - Must include one sentence on why a column store helps a SUM over one column - Must include one sentence on a job DuckDB should refuse - Edge cases / traps - DuckDB is one writer. It is not a multi-user OLTP server. - Types and timestamps surprise people coming from Pandas or Postgres - Extensions are powerful and also a trust boundary - A query that looks cheap in SQL can explode memory on a bad join - "It is fast on my laptop" is not a warehouse design - Application task - Written explanation from zero, plus one defended sketch - The sketch names storage layout, execution model, and the tool you would not pick - Name one failure mode (single writer, memory blow-up, or wrong engine for OLTP) - Video pair (required) - HyperFrames: the HTML composition for the day (explainer of the sketch) - Remotion: a React companion that plays the same beats, built by Codex CLI on this machine (codex exec) - Same story, two runtimes. Remotion does not replace the HyperFrames cut. It sits beside it. - Out of scope for the pair: porting Remotion back into HyperFrames (/remotion-to-hyperframes) unless asked later
