Every narration line and question card from the deep-dive cut, with the slide it belongs to.

Opening. Welcome to the technical deep dive on DuckDB. This cut walks the NotebookLM slides: the in-process engine, how a query runs, and where DuckDB should refuse the job.

Slide 1: Title

Slide 1 titles the cut. DuckDB, the in-process analytical blueprint. Engine mechanics, architectural limits, and how to decide for single-node OLAP.

Slide 2: The bottleneck

Question card: What cost does an in-process engine remove?

The socket, the client protocol, and the copy of each result row back to the application. The query and the program share one address space.

Example: A Python process calls DuckDB and reads the result from memory instead of from a remote database.

Slide 2 says the old bottleneck was not the join. It was the client-server hop: serialization, network latency, and a client protocol. DuckDB sits inside the application, so the query uses shared memory instead of a socket.

Slide 3: Missing quadrant

Question card: Which quadrant is DuckDB claiming?

In-process, and analytical. Not in-process OLTP, and not a client-server warehouse. SQLite already owns embedded transactions. DuckDB is for scans and aggregates.

Example: Summing one column of a Parquet file on the laptop, not updating one order row for a live user.

Slide 3 places DuckDB in the missing quadrant. SQLite is in-process and transactional. Postgres and MySQL are client-server OLTP. Snowflake and ClickHouse are client-server OLAP. DuckDB is in-process OLAP: local analytics on large data.

Slide 4: Columnar storage

Question card: Why does a column store read less for a SUM?

Values of one column sit together on disk. The other columns stay unread. An analytical query names a few columns out of a wide table.

Example: SUM of Amount reads the Amount stripe and skips Name and Date.

Slide 4 is the storage layout. A row store must read the whole row to sum Amount. DuckDB stores each column together, so that sum reads the Amount column and leaves the rest on disk.

Slide 5: Vectors of 2048

Question card: What is a DataChunk?

A batch of 2048 tuples in columnar layout. Operators run on the batch. The batch stays in cache. A row-at-a-time loop keeps missing out to main memory.

Example: Filter, projection, and aggregate each see the same 2048-row chunk.

Slide 5 is vectorized execution. DuckDB does not pull one row at a time through filter, projection, and aggregate. It moves a DataChunk of 2048 tuples, kept in cache. Row-at-a-time work falls out to main memory, which the slide marks as about one hundred times slower.

Slide 6: Morsels

Question card: How do morsels differ from a fixed hash split?

Threads pull the next morsel from a queue instead of owning one partition for the whole query. A hot key cannot leave the other cores idle.

Example: One customer id is huge. Idle threads take more morsels instead of waiting on that partition.

Slide 6 is morsel-driven parallelism. A fixed hash partition stalls when one key is huge and the other threads sit idle. DuckDB puts morsels on a task queue. An idle thread takes the next morsel, so skew does not park the machine.

Slide 7: Zero-copy scans

Question card: What can DuckDB scan without a load step?

CSV, Parquet, a Pandas data frame, and Arrow. The scanner reads the source. Parquet can also skip row groups with predicate pushdown.

Example: SELECT SUM of amount FROM a Parquet path, with no CREATE TABLE first.

Slide 7 is the zero-copy router. You do not have to load a file into a DuckDB table first. Scanners read CSV, Parquet, a Pandas frame, or Arrow. Parquet can push the filter down. Arrow and data frames can be read from memory.

Slide 8: One writer

Question card: When may a second process open the same file?

Only for reading, and only if that connection is read-only. A second writer is blocked. DuckDB keeps one writer process so it can cache data and the catalog in RAM.

Example: Three report jobs open the file read-only. A second process that tries to INSERT is refused.

Slide 8 is the concurrency contract. One process may write, and that process may use many threads for a bulk update. A second process that tries to write is blocked. Other processes may read only when the file is opened read-only.

Slide 9: Extensions

Question card: Why are httpfs and Iceberg extensions, not the core?

The core stays free of external libraries. Remote IO and table formats load beside it. The binary stays small, and a closed room can refuse the download.

Example: Querying S3 loads httpfs. A laptop scan of a local Parquet file does not need it.

Slide 9 is the extension surface. The core ships with no external libraries. JSON, spatial, Iceberg, and httpfs, including S3, load beside the core. The slide notes that httpfs links OpenSSL so the core binary does not carry that weight.

Slide 10: Where it fits

Question card: When is Spark the wrong tool on this matrix?

When the working set fits one machine. Spark's cluster setup is the cost, not the scan. DuckDB is the single-node OLAP row of the table. Spark is the petabyte row.

Example: A 40 gigabyte Parquet folder on a laptop does not need a JVM cluster.

Slide 10 is the fit matrix. SQLite for point reads and writes. Postgres when you need a server and mixed work. Spark when the data needs a cluster. DuckDB when the analytical working set fits one machine's RAM and disk.

Slide 11: Day-one traps

Question card: What does Database locked usually mean?

Two processes tried to write, or two transactions conflicted on the same rows. The file allows one writer process. Optimistic conflicts fail the second transaction.

Example: A notebook and a script both INSERT into the same database.duckdb file.

Slide 11 is the day-one ledger. Database locked means two writers, or a transaction conflict. An out-of-memory crash on a join means the plan built an intermediate it could not spill. A network drive can corrupt the file or stall on weak locks. The fixes on the slide are: rerun the transaction, gather statistics and reorder the join, and keep the working file on a local drive.

Slide 12: Decision packet

Question card: What should a team stop doing if this decision holds?

Starting Spark for data under one machine, and writing a loader just to look at a CSV. The analytical question can run in the process, against the file.

Example: An analyst sandbox queries Parquet directly instead of waiting on a warehouse load.

Slide 12 is the decision. Standardize on DuckDB for local pipelines, data-science work, and analyst sandboxes. Stop starting a Spark cluster for data that fits one machine, and stop writing a loader just to query a CSV or a Parquet file.

Recap

We covered the missing quadrant, columnar storage, vectors of 2048, morsel-driven parallelism, zero-copy scans, one writer, extensions, and the traps that show up on day one.
