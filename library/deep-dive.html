Mastery deep dive — DuckDB

Naming first. This note is about DuckDB, the in-process analytical database at duckdb.org. It is not DuckTV, not a television product, and not a client-server warehouse you connect to by default. The engine is an MIT-licensed C++ library. The intellectual property sits with the DuckDB Foundation. MotherDuck is a separate cloud product that can attach to a local engine. Docs: duckdb.org/docs.

Pack. This report sits on the one-day mastery hub 00 - DuckDB Hub. The study blocks, the source ledger, and the NotebookLM exports are the inputs. The day itself has not been sat.

Executive take

DuckDB is a column store that runs inside your process. You give it SQL. It reads the columns the query names, in batches, on all the cores of one machine. There is no server to install for the local case.

Use it for local and embedded analytics: Parquet, CSV, JSON, Arrow, and data frames, plus a single .duckdb file when you want the result to persist. Do not use it as the multi-user system of record. One process writes. Many processes may read only when the file is opened read-only.

The NotebookLM decision packet recommends standardizing local and embedded analytical work on DuckDB, and writing the single-writer rule down before anyone treats it as a shared database. That recommendation matches the official concurrency page. The packet's speed multiples and "sub-second on a billion rows" lines are briefing claims. Measure them on your files before you repeat them.

What the engine is

Five words, then the engine.

Word Meaning
Table A named relation of typed columns.
Query A SQL statement. The engine picks the physical steps.
Join Match rows from two relations on a predicate.
OLTP Many small row reads and writes. Postgres and SQLite are built for this.
OLAP Few large scans and aggregates over a few columns. DuckDB is built for this.

Row storage writes a whole record together. A SUM on one column still reads the other columns. Column storage writes each column together. The same SUM reads that column. That is why a column store wins the analytical scan and loses the single-row lookup.

DuckDB then executes in vectors. A Vector is one column slice. A DataChunk is a set of those vectors, one chunk of a row. Official internals: the default STANDARD_VECTOR_SIZE is 2048 tuples (Execution format). Operators run on the chunk, not on one row at a time, so the working set stays in cache. Hannes Mühleisen's public account of the same idea: a main-memory reference is on the order of 100 nanoseconds, an L1 reference is a fraction of a nanosecond, and vectorized execution is how a SQL pipeline stays in the fast memory.

Morsel-driven parallelism splits a pipeline into chunks and hands those chunks to threads. The idea comes from the HyPer / TUM line (Leis, Boncz, Kemper, Neumann), not from the SIGMOD 2019 demo paper. DuckDB adopted it. Skew is the failure mode the talks name: one hot key can stall a static split. Dynamic morsels are the mitigation.

Out of core. Intermediate state can spill when the working set exceeds RAM. A bad join can still exhaust memory before the spill helps. EXPLAIN and EXPLAIN ANALYZE are how you see the scan, the join, and the aggregate before you trust a number.

Replacement scan. A file path or a data frame can stand in for a table name. The query reads Parquet or CSV without a load step. CSV and JSON type detection samples early rows and can guess wrong. Parquet carries min/max stats the scanner can use. Declare types when the sample is a lie.

Where it stands

Engine Built for Pick it when
DuckDB In-process OLAP, one machine The working set fits one box and the question is a scan, join, or aggregate
PostgreSQL Server OLTP, many writers The database is the live system of record
SQLite In-process OLTP The app stores rows and looks up one row at a time
Polars Dataframe API The pipeline is Python or Rust expressions, not a SQL catalog
Spark A cluster The data will not fit one machine, or a dead node must not kill the job
MotherDuck Shared cloud warehouse on DuckDB More than one person must share the database, and a cloud account is allowed

SQLite and DuckDB share the embedded, single-file shape and almost nothing else. Postgres keeps the truth. DuckDB scans a copy or the files. Spark is the scale-out tool. Polars is the dataframe tool. A 2026 Information Systems review of single-node SQL engines is the literature pointer for "one node is enough." It is not a DuckDB product review. See 2026-10-10 - Competitors and closed lab.

How a query actually runs

Sketch this before you defend a plan. Events in Parquet, a small dimension table, one aggregate.

  1. Scan the event file. Read only the columns the query names. Zone stats skip row groups when a filter is selective.
  2. Build a hash table on the small dimension. Probe it from the event scan. If you build on the huge side, memory blows up.
  3. Aggregate in a pipeline that can run while the scan is still producing chunks.
  4. Threads take morsels of that pipeline. They do not each run a private copy of the whole query from scratch.
  5. EXPLAIN should show the scan, the join, and the aggregate. If the tree materializes a giant intermediate, the SQL is cheap and the plan is not.

The SIGMOD 2019 paper (Raasveldt and Mühleisen, doi:10.1145/3299869.3320212) is the system paper: an analytical engine with SQLite's in-process shape. MonetDBLite (2018) is the predecessor by the same authors. Vectorized execution itself is older. Boncz's later writing treats it as a twenty-year technique. DuckDB uses it. DuckDB did not invent it.

Concurrency, extensions, and the host process

Official rule (Concurrency):

  • One process may read and write.
  • Inside that process, appends do not conflict. Two threads that edit the same row can. The second transaction fails. That is optimistic concurrency, not a lock queue you can lean on.
  • Several processes may read the same file only in access_mode = 'READ_ONLY', and none of them may write.
  • DuckDB caches data, the catalog, and function pointers in RAM so the next query is fast. Another process writing the file invalidates that cache. Network drives with weak locks are a known way to corrupt that story.

The NotebookLM edge catalog also names a host-process failure: an embedded engine lives in the application. A fatal fault can take the Python or JVM process with it. A client-server database crashes in the other process. That is the trade for having no socket.

Extensions keep OpenSSL, ICU, and remote IO out of the core binary. They run with the rights of the DuckDB process. Default installs can fetch a signed extension from extensions.duckdb.org the first time a query needs it. In a closed environment that fetch is the bug. Turn auto-install and auto-load off, leave community and unsigned extensions off, and ship the binaries you trust. Docs: Securing extensions.

The NotebookLM catalog mentions Quack (a remote protocol, described there as beta around DuckDB 1.5.2) and DuckLake (a table format with a Postgres catalog, described there as 1.0 in April 2026) as ways to get multi-writer behavior. Those names came from the generated briefing. They were not re-checked against a release note in this writing pass. Do not treat them as the concurrency contract. The contract is the concurrency page above.

Closed lab versus cloud

Local DuckDB does not need an account. Opening a .duckdb file, or using memory only, does not contact MotherDuck. That is why it is a reasonable proposal for an air-gapped process.

It is not an authorization to process classified data. Elicit returned no paper that evaluates DuckDB in a classified lab. The nearby papers are SQLite in a trusted execution environment (Smaug, 2023; BiTDB, 2024). They describe a problem. They do not certify this engine. A lab still approves the binary, the extensions, and the machine.

Situation What runs What must stay off
Closed lab The local library, files on disks that lab already trusts ATTACH 'md:', extension auto-install, community and unsigned extensions, queries that reach the public internet
Your own cloud VM The same local library, on a machine you control MotherDuck, unless that account is separately approved
MotherDuck Their cloud warehouse, plus optional hybrid execution Any claim that this is still the closed lab

MotherDuck's architecture docs and the CIDR 2024 paper (Atwal et al., p46) describe dual execution: a query can run locally, in their cloud, or split. ATTACH 'md:' is the step that leaves the machine. Hybrid execution is a feature in a cloud account. It is the wrong feature in a classified room.

Claim in the NotebookLM packet How to hold it

"10× to 100×" versus client-server, or "1 billion rows in ~157 ms" Briefing lines. They are not an SLA. Time your files.
Quack and DuckLake as the multi-writer path Named in the generated catalog. Confirm on a release note before you design on them.
DuckDB is approved for classified data Not in any source in this pack.

When not to use it

  • Many people must write at once.
  • The workload is point lookups and small transactions. Use SQLite or Postgres.
  • The working set, including join state, will not fit one machine. Use a cluster.
  • You need the database to be a separate process so an engine fault cannot kill the application.
  • The environment cannot allow an extension download or a MotherDuck attach, and you have not vendored the binary.
  • A single fast laptop query is being treated as a warehouse design.
