Intake — DuckDB

Date: 2026-10-10
Mode: B (interview → draft mind map)

Mission snapshot

  • Outcome: By the end of the day, explain DuckDB from zero and sketch one local analytics query you could defend. The sketch names the storage layout, the execution model, and when DuckDB beats Postgres, SQLite, Polars, or Spark. Success is a short written explanation plus that sketch, with one named failure mode.
  • Audience: Self-study. Own fluency so Aaron can place DuckDB in an architecture conversation. Not an exam and not a customer deliverable today. The teach-it block is practice for that conversation.
  • Depth: Working fluency across the engine, not a survey of every SQL function and not a single-subsystem deep dive. Enough to sketch a scan-join-aggregate and say why the engine runs it that way. A later day can go deep on one slice (vectorized execution, or the storage format).
  • Constraints: Eight hours available. The pack's focused blocks are about 5.5 hours. Extra time is source reading. Prefer official docs, the DuckDB paper, and at least two named talks. No cluster build and no install lab is required.

Interview answers

outcome

By the end of the day, explain DuckDB from zero and sketch one local analytics query you could defend. The sketch names the storage layout, the execution model, and when DuckDB beats Postgres, SQLite, Polars, or Spark. Success is a short written explanation plus that sketch, with one named failure mode.

audience

Self-study. Own fluency so Aaron can place DuckDB in an architecture conversation. Not an exam and not a customer deliverable today. The teach-it block is practice for that conversation.

prior_knowledge

Assume zero. Define a table, a query, a join, OLTP versus OLAP, and row storage versus column storage before any DuckDB-specific term. Do not assume the CLI, Parquet, or EXPLAIN.

boundaries

Must include: what DuckDB is (in-process SQL database), row versus column storage, vectorized execution, morsel-driven parallelism, the single-file database, reading Parquet and CSV, EXPLAIN at a sketch level, extensions in outline, and when not to use DuckDB.

Out of scope: a production deploy, building a DuckDB extension in C++, distributed DuckDB clusters, and multi-week academy depth. No local lab is required today.

depth

Working fluency across the engine, not a survey of every SQL function and not a single-subsystem deep dive. Enough to sketch a scan-join-aggregate and say why the engine runs it that way. A later day can go deep on one slice (vectorized execution, or the storage format).

constraints

Eight hours available. The pack's focused blocks are about 5.5 hours. Extra time is source reading. Prefer official docs, the DuckDB paper, and at least two named talks. No cluster build and no install lab is required.

falsifiers

The day is a waste if it is a feature tour of SQL syntax that never says how columnar storage and vectorized execution change a query, and never names when Postgres, SQLite, Polars, or Spark is the better tool.
