DuckDB Architecture and In-Process Analytics: Comprehensive Study Guide

1. Core Architectural Concepts & Frameworks

Overview and System Purpose

DuckDB is an embeddable, in-process, Open-Source Analytical Database Management System (OLAP DBMS) written in C++11 (built via CMake) with no external dependencies. Designed by Mark Raasveldt and Hannes Mühleisen at the CWI (Centrum Wiskunde & Informatica) in Amsterdam and introduced at SIGMOD 2019, DuckDB addresses a structural gap in database architecture: while SQLite serves as an ubiquitous in-process engine for transactional processing (OLTP), DuckDB provides an unobtrusive, zero-dependency, in-process engine optimized for analytical processing (OLAP).

Key Architectural Pillars

1. In-Process Execution Model vs. Client-Server Architecture

Traditional database management systems (e.g., PostgreSQL, MySQL, Oracle) operate on a client-server paradigm dating back to the mid-1980s. Client-server systems rely on an independent server process that clients connect to via IPC sockets or network protocols. 

Client-Server Model:
[ Host Application ]  <--- (Socket / IPC Protocol Overhead) --->  [ Database Server Process ]

In-Process Model (DuckDB):
[ Host Application  |  DuckDB Engine (Linked Library) ]  <--->  (Zero-Copy Shared Memory)

This traditional model introduces significant friction: * Administrative & Setup Friction: Requires service configuration, socket/port listening setup, user access control (pg_hba.conf), and server lifecycle management. * Data Transfer Overhead: Query execution requires data serialization, transmission across IPC/network boundaries, and deserialization on the client side. Client protocol transfers can be over 100x slower than raw memory bandwidth. * In-Process Advantages: DuckDB links directly inside host processes (such as Python, R, Java/JDBC, C++, or WebAssembly). Queries execute within the host thread’s memory address space. This enables zero-copy integration with host data structures (e.g., Pandas DataFrames, Apache Arrow tables), allowing DuckDB to scan and transform external memory without copy or serialization overhead.

2. OLTP vs. OLAP Workloads

  • OLTP (Online Transaction Processing): Characterized by frequent, small, point-based reads and updates touching entire individual rows (e.g., inserting an order, looking up a user record). Engines utilize row-oriented layouts and B-Trees to ensure ACID guarantees and transactional isolation.
  • OLAP (Online Analytical Processing): Characterized by complex, long-running queries scanning millions or billions of rows to compute aggregations (SUM, AVG, COUNT), filtering, and multi-table joins. Aggregations touch a small subset of total columns across huge numbers of rows.

3. Row Storage vs. Column Storage

  • Row Storage (Row-Major): Stores complete tuple attributes contiguously on disk and in memory ($R_1C_1, R_1C_2, R_1C_3, R_2C_1, R_2C_2, \dots$). Scanning a single attribute requires reading all adjacent column data into the CPU cache, wasting memory bandwidth.
  • Column Storage (Column-Major): Stores distinct attributes contiguously across rows ($R_1C_1, R_2C_1, R_3C_1 \dots R_1C_2, R_2C_2 \dots$). If an analytical query requests a SUM(sales) across a table with 100 columns, DuckDB reads only the sales column off disk/RAM, skipping 99% of non-relevant data.

4. Vectorized Query Execution vs. Alternative Paradigms

Query execution engines process operations across three primary paradigms:

Volcano (Row-at-a-Time):  [ Operator 1 ] --( 1 Row )--> [ Operator 2 ] (High Overhead)
Full Materialization:     [ Operator 1 ] --( All Rows )-> [ Operator 2 ] (High RAM Consumption)
Vectorized Processing:    [ Operator 1 ] --( 2048 Chunk )-> [ Operator 2 ] (CPU Cache Resident)
  1. Row-at-a-Time (Volcano / Iterator Model): Used by PostgreSQL and SQLite. Operators call next() to pull one row at a time. This causes high virtual function dispatch overhead, CPU instruction cache invalidation, and poor instruction-level parallelism.
  2. Full Materialization: Used by naive data framing tools (e.g., early Pandas). Each operator processes and writes the complete result set to memory before passing it to the next operator. This consumes massive RAM bandwidth and risks out-of-memory crashes.
  3. JIT Compilation (Just-In-Time LLVM): Compiles SQL queries into machine assembly code at runtime. While fast, it requires bundling massive compiler toolchains (LLVM dependencies), increases binary size significantly, and incurs high query compilation latency.
  4. Vectorized Processing (DuckDB / MonetDB/X100): Pioneered by Peter Boncz et al. Operators process fixed-size batches of column arrays called Vectors (STANDARD_VECTOR_SIZE default = 2048 tuples). This batching keeps execution data within CPU L1/L2/L3 cache (e.g., 32 MB die cache), eliminates per-row virtual function dispatches, maximizes CPU instruction cache efficiency, and optimizes hardware branch prediction and speculative execution.

5. Morsel-Driven Parallelism

DuckDB parallelizes execution across CPU cores using morsel-driven parallelism (developed by Leis et al. at TUM): * Pipeline Breaking: Queries are divided into executable pipelines delimited by pipeline breakers—blocking operators (e.g., Hash Join build sides, Hash Aggregates, Sorts) that must collect all input tuples before producing output. * Dynamic Task Slicing: Rather than using static exchange operators (Volcano-style), which use fixed hash partitioning of data streams and suffer from data skew (the "Justin Bieber problem," where one heavy partition stalls a thread while others sit idle), morsel-driven processing dynamically divides data scanning tasks into small chunks ("morsels"). * Lock-Free Scheduling: Worker threads pull morsels from a shared queue on demand. If one thread encounters a dense chunk, remaining threads pull available morsels dynamically, ensuring uniform CPU utilization across multi-core systems.

6. Concurrency and Multi-Version Concurrency Control (MVCC)

  • Single-Process Engine: DuckDB executes embedded inside a single host process.
  • Read-Write Access Mode: Exactly one process can hold a read-write connection to a DuckDB database file. Within that single writer process, concurrent writing across multiple threads is supported using Bulk MVCC and Optimistic Concurrency Control (OCC). Appends never conflict; concurrent updates/deletes to separate tables or non-overlapping row subsets succeed. Simultaneous edits to the exact same row cause transaction conflict errors (Transaction conflict: cannot update a table that has been altered!).
  • Read-Only Access Mode: Multiple processes can concurrently read from the database file if initialized with access_mode = 'READ_ONLY'.
  • Multi-Process Concurrency Solutions: Multi-process concurrent writing requires either the Quack remote client-server protocol or the DuckLake format using a PostgreSQL catalog for cross-instance state coordination.

2. Execution Engine Internals & Data Representation

The Execution Vector Format

In DuckDB, memory vectors are represented logically as arrays carrying data of a single data type. To optimize performance, DuckDB uses multiple internal physical vector formats to store logical data efficiently:

[Logical Vector Array]
  ├── Flat Vector:       [ Contiguous Physical Memory Array ]
  ├── Constant Vector:   [ Single Value ] (Repeated implicitly across 2048 tuples)
  ├── Dictionary Vector: [ Child Vector ] + [ Selection Vector (Indexes) ]
  └── Sequence Vector:   [ Offset Base ] + [ Increment Step ]
  1. Flat Vectors: The uncompressed physical baseline. Logical values are stored in contiguous memory blocks.
  2. Constant Vectors: Stores a single physical value representing identical values across all rows in a chunk (e.g., constant expressions like SELECT lst || 'duckdb' FROM range(1000)). Reduces memory overhead and execution costs to $O(1)$.
  3. Dictionary Vectors: Composed of a child Vector and a selection vector containing integer indices pointing to elements in the child Vector. Emitted during storage decompression to allow operations on compressed data without full decompression.
  4. Sequence Vectors: Stores a base offset and an increment step value. Used to store sequence ranges and internal row identifiers efficiently without allocating arrays.
  5. Unified Vector Format (UnifiedVectorFormat): Provides a standardized interface for accessing vector data regardless of physical underlying representation, preventing exponential growth in function overload variants.

Complex Data Types & Memory Formats

DuckDB uses specialized memory representations for complex and variable-length types:

String Vectors (string_t)

Variable-length text is managed through an inlined struct design:

struct string_t {
    union {
        struct {
            uint32_t length;
            char prefix[4];
            char *ptr;
        } pointer;
        struct {
            uint32_t length;
            char inlined[12];
        } inlined;
    } value;
};
  • Inlined Strings ($\le 12$ Bytes): Stored directly inside the 16-byte string_t buffer. Eliminates pointer chasing and heap allocations.
  • Long Strings (> 12 Bytes): Stores a 4-byte length, a 4-byte string prefix, and an 8-byte pointer to an auxiliary string heap memory block. The 4-byte prefix enables quick comparisons; if prefixes differ, the engine avoids dereferencing the pointer.

Nested Complex Types

  • List Vectors: Composed of a child Vector containing underlying scalar values and an array of list_entry_t structs (offset, length). Offsets point to ranges in the child Vector. Supports recursive nesting (e.g., BIGINT[][]).
  • Array Vectors: Used for fixed-length array types (INTEGER[3]). Does not require per-row list_entry_t structures; elements map contiguously to child vector positions at index range $[i \times \text{array_size}, (i + 1) \times \text{array_size})$.
  • Struct Vectors: Contains an ordered list of named child vectors defined by the struct schema.
  • Map Vectors: Represented internally as LIST[STRUCT(key KEY_TYPE, value VALUE_TYPE)].
  • Union Vectors: Represented internally as a STRUCT. Child 0 is a Tag Vector indicating the active type for each row.

Query Pipeline Execution & Subquery Unnesting

  1. Parsing & Binding: SQL strings are parsed using an extended PostgreSQL parser (libpg_query). The binder verifies table schemas, resolves data types, and constructs a logical plan tree.
  2. Logical Optimization: Applies static rewrites, such as selection pushdown (moving filters beneath joins) and projection pushdown (pruning unreferenced columns).
  3. Subquery Unnesting: Implements optimization algorithms based on research by Neumann, Kemper, and Neumann & Radke. Correlated subqueries are flattened into relational join and aggregate operators, preventing costly $O(N^2)$ tuple-by-tuple re-executions.
  4. Physical Planning & Execution: Logical operators are translated into physical operators (e.g., Hash Join, Physical Projection). Pipelines are constructed and scheduled dynamically across worker threads via morsel-driven execution.

3. Short-Answer Practice Quiz

Questions

  1. How does DuckDB’s in-process architectural model eliminate client protocol overhead compared to client-server systems like PostgreSQL?
  2. Why does a columnar storage engine outperform a row-oriented storage engine when executing aggregate functions like SUM() over a single column?
  3. What is the standard vector size (STANDARD_VECTOR_SIZE) in DuckDB's vectorized execution engine, and why is vector size capped at this specific scale?
  4. Explain how morsel-driven parallelism handles data skew (the "Justin Bieber problem") better than traditional Volcano-style exchange operators.
  5. What are the concurrency rules for single-process writing in DuckDB, and what occurs when two concurrent threads attempt to modify the exact same row?
  6. Describe the physical memory layout of the string_t structure for strings of length 12 bytes or fewer versus strings longer than 12 bytes.
  7. What is the role of DuckDB’s UnifiedVectorFormat within the execution engine?
  8. Explain the concept of a "replacement scan" when DuckDB queries external files like Parquet or JSON directly.
  9. Why did DuckDB’s creators choose a vectorized execution model over JIT compilation via LLVM?
  10. Under what operational conditions should DuckDB be selected over Apache Spark, and when does Apache Spark remain the superior choice?

Answer Key

  1. In-process vs. Client-Server Overhead: Client-server databases require data serialization, IPC or network socket transmission, deserialization, and authentication handling (pg_hba.conf). DuckDB runs directly inside the application process's memory space, eliminating network latency and permitting zero-copy query execution on native host data structures like Pandas DataFrames or Apache Arrow tables.
  2. Columnar Advantage for Aggregations: Columnar storage places values of a single attribute contiguously in memory and on disk. An aggregate query over a single column reads only that column's data blocks, skipping all other non-relevant table columns and maximizing I/O and cache efficiency.
  3. Standard Vector Size: The default STANDARD_VECTOR_SIZE is 2048 tuples. This size ensures that working intermediate vector chunks fit completely within CPU L1/L2/L3 caches (e.g., die cache), minimizing main memory bus accesses and maximizing instruction execution efficiency.
  4. Handling Data Skew: Exchange operators statically partition streams using fixed hashes, causing threads assigned dense keys to stall while other threads sit idle. Morsel-driven parallelism dynamically assigns small data chunks ("morsels") to a thread work pool on demand, ensuring that threads pull remaining tasks dynamically if one morsel takes longer to execute.
  5. Single-Process Concurrency Rules: Only one process can open a database file in read-write mode. Within that writer process, multiple threads write concurrently using Bulk MVCC and Optimistic Concurrency Control (OCC); appends never conflict, but simultaneous edits to the exact same row throw a transaction conflict error (Transaction conflict: cannot update a table that has been altered!).
  6. string_t Memory Layout: Strings $\le 12$ bytes are inlined directly within the struct buffer, eliminating pointer chasing. Strings $> 12$ bytes store a 4-byte length, a 4-byte prefix for early-out comparisons, and an 8-byte pointer to heap memory.
  7. Unified Vector Format: UnifiedVectorFormat provides a generic view abstraction over all underlying physical vector representations (Flat, Constant, Dictionary, Sequence). It allows functions and operators to operate on vector data uniformly without generating combinatorial code expansions for every vector type variant.
  8. Replacement Scans: Replacement scans automatically intercept table names in SQL queries that match local file paths or host program variables (e.g., FROM 'data.parquet'). The engine inferentially generates temporary schemas and binds file scanners without requiring data loading into database tables.
  9. Vectorization vs. JIT Compilation: JIT compilation requires bundling large compiler infrastructure (like LLVM), increases binary footprint, and adds runtime compilation latency. Vectorized execution achieves equivalent query execution speeds while keeping the engine lightweight, zero-dependency, and instantly executable.
  10. DuckDB vs. Apache Spark Trade-offs: DuckDB excels at single-node local analytics where datasets fit on local disk or memory (the "99%" of analytics problems), avoiding cluster setup and network overhead. Apache Spark is required for distributed petabyte-scale computations across multi-node clusters that exceed single-machine hardware limits.

5. Glossary of Important Terms

  • DuckDB: An embeddable, in-process, columnar, analytical SQL database management system written in C++11 and designed for high-performance zero-dependency OLAP query execution.
  • In-Process Database: A database engine running directly inside the host application's process and memory space rather than running as a separate server daemon.
  • OLAP (Online Analytical Processing): Database workloads characterized by multi-row scans, complex joins, and aggregations over columnar layouts.
  • OLTP (Online Transaction Processing): Database workloads characterized by frequent, small point reads and updates requiring strict ACID properties over row-oriented layouts.
  • Columnar Storage: A physical storage design where attribute values across rows are stored contiguously in memory and on disk.
  • Vectorized Query Execution: A processing paradigm where database operators process fixed-size batches of column arrays (vectors) at a time to maximize CPU L1/L2/L3 cache residence and instruction efficiency.
  • STANDARD_VECTOR_SIZE: The fixed default chunk size processed by DuckDB execution operators, configured to 2048 tuples.
  • Flat Vector: The uncompressed baseline physical vector format where data values are stored contiguously in memory.
  • Constant Vector: A physical vector format storing a single scalar value implicitly repeated across an entire vector chunk.
  • Dictionary Vector: A physical vector format composed of a child vector and an integer selection vector, allowing processing on compressed data without full decompression.
  • Sequence Vector: A physical vector format defined by a base offset and a step increment, used for sequence ranges and row identifiers.
  • UnifiedVectorFormat: A generic view interface in DuckDB that allows operators to read values from any physical vector representation uniformly.
  • Morsel-Driven Parallelism: A dynamic thread execution framework where query pipelines pull small work units ("morsels") from a shared queue, preventing worker thread stalling due to data skew.
  • Pipeline Breaker: An operator (e.g., Hash Join build, Group By aggregate, Sort) that must collect all input tuples before passing output to subsequent operators.
  • Bulk MVCC: A Multi-Version Concurrency Control implementation optimized for bulk appending and updating of large column blocks rather than individual row edits.
  • Optimistic Concurrency Control (OCC): A transactional concurrency mechanism where modifications proceed without lock acquisition, failing with a transaction conflict error if concurrent edits overlap the same row.
  • string_t: DuckDB's string memory representation, inlining strings $\le 12$ bytes directly inside the struct and storing longer strings via a 4-byte prefix, length, and pointer.
  • Replacement Scan: A mechanism where file paths or host program variables in SQL queries are dynamically mapped to external reader functions without explicit table creation.
  • DuckLake: An open specification and storage format allowing DuckDB instances to perform concurrent multi-process writes using a central PostgreSQL database as a catalog.
  • Quack Remote Protocol: A client-server wire protocol for DuckDB that enables multi-process access over a network.
  • MonetDBLite: An embedded analytical database created by Raasveldt and Mühleisen in 2018; served as the immediate conceptual predecessor to DuckDB.
