DuckDB Technical Working Briefing: Architecture, Core Mechanics, and Domain Mental Models

1. Domain Framing & Engine Positioning

DuckDB is an in-process, embeddable, column-oriented Online Analytical Processing (OLAP) database engine written in C++11 with zero external dependencies. It is engineered to execute high-performance analytical SQL queries directly inside an application host process (such as Python, R, Java, Node.js, or compiled C/C++ applications) without requiring a client-server network protocol, background service daemon management, socket configuration, or administrative oversight.

For a data systems practitioner, working fluency in DuckDB requires the capability to explain query execution mechanics from first principles, construct and defend physical scan-join-aggregate execution plans, articulate the hardware cache locality benefits of vectorized execution and morsel-driven parallelism, and rigorously evaluate structural trade-offs to determine where DuckDB outperforms alternative engines versus where it must be rejected.

2. Prerequisite Vocabulary & Foundational Concepts

Before inspecting DuckDB's execution mechanics, five foundational database concepts must be established:

  1. Table, Query, and Join: A table is a named logical relation composed of structured rows and typed columns. A query is a declarative SQL statement specifying a data retrieval or transformation operation. A join is a relational operator that correlates tuples from two or more tables based on evaluation of matching key predicates.
  2. OLTP (Online Transaction Processing): A database workload pattern dominated by high volumes of rapid, low-latency transactions (e.g., single-row point lookups, insertions, updates, and deletes) requiring strict ACID isolation and fine-grained row access control.
  3. OLAP (Online Analytical Processing): A database workload pattern dominated by complex, read-heavy queries that scan, filter, and aggregate millions or billions of rows across a narrow subset of columns to produce summary metrics and multidimensional reporting.
  4. Row-Oriented Storage: A physical storage layout where all attribute values belonging to a single record are written contiguously in memory or on disk before the next record begins (the standard layout in transactional engines like PostgreSQL and SQLite).
  5. Column-Oriented Storage: A physical storage layout where all scalar values for a given column across all rows are stored contiguously together, completely isolated from adjacent columns.

Note: Columnar storage dramatically accelerates analytical aggregations (such as SUM(sales) over a 100-million row table) because the execution engine accesses and transfers only the specific byte ranges allocated to the sales column. In a row-oriented engine, calculating that same aggregate forces the storage manager to stream complete, multi-attribute tuples (containing unrequested strings, timestamps, and metadata) off disk and into RAM, congesting the hardware bus and thrashing CPU L1/L2 caches. Furthermore, contiguous arrays of uniform primitive types eliminate instruction cache invalidations and allow modern hardware branch predictors and SIMD registers to execute at peak theoretical throughput.

3. Core Engine Architecture & Vectorized Execution

DuckDB is constructed as an embeddable C++11 library compiled via CMake without third-party external library dependencies. It executes entirely inside the host process's memory space, completely eliminating client-server IPC protocols, network socket handshakes, and serialization bottlenecks.

Vectorized Execution Engine Mechanics

DuckDB implements a vectorized query processing model directly descended from the MonetDB/X100 architectural lineage (Boncz et al.). Traditional engines process data using the Volcano "Tuple-at-a-Time" model, which invokes virtual function calls for every individual attribute of every row, incurring catastrophic function dispatch overhead and instruction cache invalidations. Conversely, full in-memory materialization engines process entire column arrays at once, which rapidly exhausts hardware L1/L2/L3 caches and forces memory traffic out to main RAM.

DuckDB resolves this trade-off by streaming fixed-size batches of column values called Vectors:

  • Standard Vector Size: Controlled by the global compilation constant STANDARD_VECTOR_SIZE = 2048 tuples.
  • DataChunk Abstraction: A DataChunk represents a physical horizontal slice of a dataset, composed of a collection of type-specific Vector references representing the target columns. Operators pass DataChunk references down physical pipeline trees.

Hardware Memory Latency Hierarchy & Vector Size Rationale

The core design target of vectorized processing is anchoring the engine's active working memory set inside the hardware CPU cache hierarchy. Hannes Mühleisen’s architectural model highlights the extreme latency differentials governing modern processing:

$$\text{CPU Register } (1 \text{ cycle}) \longrightarrow \text{L1/L2 Cache } (\sim 0.5 \text{ ns}) \longrightarrow \text{Main Memory / RAM } (\sim 100 \text{ ns})$$

Main RAM accesses incur a severe $\sim 200\times$ speed penalty relative to L1 cache reads. By constraining batch execution to $2048$ tuples per DataChunk, DuckDB ensures that intermediate data vectors fit comfortably within standard $32\text{ KB}$–$512\text{ KB}$ L1/L2 cache boundaries. This eliminates the $200\times$ main memory latency penalty during pipeline execution.

Architectural Trade-off: Vectorization vs. JIT Compilation

An alternative method for eliminating Volcano interpretation overhead is Just-In-Time (JIT) compilation using LLVM (as implemented in HyPer and Umbra), which dynamically compiles SQL expressions into native machine assembly code at runtime. DuckDB explicitly rejected LLVM JIT compilation based on fundamental architectural principles:

  1. Zero External Dependencies & Binary Footprint: Shipping an LLVM compiler stack inflates binary distributions by hundreds of megabytes and introduces complex environment toolchain dependencies, violating DuckDB’s primary requirement for frictionless, zero-dependency embedding.
  2. Cold-Start & Query Latency: JIT compilation introduces a non-trivial compilation delay (often tens to hundreds of milliseconds) before query execution starts. For ad-hoc, interactive analytics over small-to-medium datasets, compilation time dwarfs actual execution time.
  3. Execution Parity: Academic benchmark studies (Kersten et al.) demonstrated that a vectorized engine processing $2048$-tuple vectors achieves hardware execution speed equivalent to JIT-compiled assembly code, while delivering instant cold-start query response.

Supported Vector Physical Representations

DuckDB utilizes specialized internal vector formats to maintain compressed data representations directly through query execution operators, avoiding unnecessary decompression copies:

Vector Format Name Physical Storage Mechanism Primary Use Cases & Optimization Triggers
Flat Vector Uncompressed, contiguous array of primitive values where physical array index directly maps to logical row index. Standard physical intermediate representation; emitted by uncompressed table scans or general operator output.
Constant Vector Single scalar value stored alongside logical array length metadata. Emitted for expression literals (e.g., 'duckdb') or constant-compressed storage blocks. Allows operators to evaluate expressions once for $2048$ rows.
Dictionary Vector Reference to a child vector holding distinct values, paired with an array of integer selection indexes. Emitted when reading dictionary-compressed disk blocks. Operators run filters/joins directly over compressed integer keys without decompressing to flat vectors.
Sequence Vector Base start offset value paired with a fixed incremental step value. Encodes sequential integer ranges without allocating memory arrays. Emitted for implicit row identifiers (rowid) or generated sequences.
Unified Vector Format Read-only abstraction layer (UnifiedVectorFormat) exposing a standardized selection vector and data pointer view over any vector. Used by complex function implementations to execute generic logic across arbitrary incoming vector types without writing specialized code paths for all format permutations.

Complex & Nested Type Handling

  • String Vectors (string_t): Uses a specialized 16-byte memory footprint: cpp struct string_t { union { struct { uint32_t length; char prefix[4]; char *ptr; } pointer; struct { uint32_t length; char inlined[12]; } inlined; } value; }; Short strings ($\le 12$ bytes) are inlined directly within the structure, avoiding heap allocation. For long strings ($> 12$ bytes), the first 4 bytes are stored as an inlined prefix alongside a memory pointer to an auxiliary heap buffer. This 4-byte prefix allows a single 32-bit integer SIMD/CPU instruction to short-circuit non-matching string comparisons instantly, eliminating pointer chasing to auxiliary memory.
  • List Vectors: Composed of a child Vector storing raw contiguous values, paired with a buffer of list_entry_t structs holding integer offset and length properties. Supports recursive nested structures (e.g., BIGINT[][]).
  • Array Vectors: Represent fixed-size lists. They eliminate per-row list_entry_t overhead by packing elements in a single child vector at physical index range $[i \times \text{array_size}, (i + 1) \times \text{array_size})$.
  • Struct Vectors: Store an ordered set of named child vectors corresponding to schema struct fields.
  • Map Vectors: Physical abstraction stored internally as LIST[STRUCT(key KEY_TYPE, value VALUE_TYPE)].
  • Union Vectors: Encapsulated using a STRUCT memory layout where the primary child vector is a Tag Vector recording the active internal type identifier per row.

4. Query Lifecycle & Morsel-Driven Parallelism

Query execution in DuckDB transitions through four physical and logical compiler stages:

[ 1. Parsing & Binding ]
   └─ libpg_query parses SQL -> Catalog binding & temp schema generation
        │
        v
[ 2. Logical Optimization ]
   └─ Projection/Selection pushdowns -> Statistics bounds -> Subquery unnesting
        │
        v
[ 3. Pipeline Construction ]
   └─ Split logical tree at blocking operators (Hash Builds/Sorts) -> Link streaming tasks
        │
        v
[ 4. Morsel-Driven Parallelism ]
   └─ Worker threads dynamically pull DataChunk morsels -> Stream through L1/L2 cache

Step-by-Step Query Processing Lifecycle

  1. Parsing & Binding: The raw SQL input string is parsed into an Abstract Syntax Tree (AST) using PostgreSQL's C parser library (libpg_query). The Binder resolves table identifiers, column names, and function signatures against catalog definitions, language DataFrames, or external file metadata.
  2. Logical Optimization: The logical plan tree undergoes rule-based and cost-based structural rewrites: * Projection & Selection Pushdowns: Predicates and required column subsets are pushed directly down to storage/file scan operators. * Metadata Statistics Pruning: Min/max statistical bounds stored in Parquet or DuckDB metadata blocks are evaluated to skip non-matching row groups entirely. * Neumann/Kemper Subquery Unnesting: Correlated subqueries are rewritten into relational join and aggregate trees using Neumann/Kemper unnesting algorithms (Neumann & Kemper 2015). This prevents row-by-row nested loop re-evaluations, delivering up to a $10,000,000\times$ (10 million-fold) query execution speedup.
  3. Pipeline Construction: Physical operators are linked into streaming pipelines bounded by "pipeline breakers" (blocking operators such as Hash Join build phases, Group-By hash aggregation builds, or Global Sorts that must consume all input tuples before emitting output).
  4. Morsel-Driven Parallelism: Multithreading is managed via dynamic worker queues based on the morsel-driven execution model (Leis et al.): * Morsel Allocation: Pipelines divide physical data scans into discrete execution morsels ($2048$-tuple DataChunk units). CPU worker threads pull available morsels dynamically from a shared task queue. * Volcano Exchange Model Contrast vs. Data Skew Mitigation: Traditional parallel engines rely on Graefe's Volcano Exchange operator model, baking static hash-partitioning exchange nodes into the physical plan. If a dataset exhibits extreme key skew (the "Justin Bieber" problem, where a single key accounts for millions of records), the exchange operator assigns that heavy key to a single thread. That worker thread maxes out while all other threads sit idle after finishing their small keys. DuckDB's morsel-driven architecture completely eliminates static exchange nodes. Workers continuously pull $2048$-tuple morsels from the global queue; if one worker hits a dense, long-running aggregation block, adjacent free threads continue pulling subsequent morsels, ensuring uniform 100% thread utilization across all CPU cores.

5. Data Ingestion, Storage Layout, and Extension Ecosystem

Replacement Scans Mechanics

DuckDB eliminates explicit CREATE TABLE and data import pipelines via Replacement Scans. When a query references a file path or in-memory object identifier (e.g., FROM 'events.parquet', FROM 'data.json', or FROM pandas_df), DuckDB executes a specific four-step dynamic binding resolution sequence:

[ 1. Binder Interception ]
   └─ Detects uncataloged string literal or identifier in FROM clause
        │
        v
[ 2. Fallback Scan Hook Trigger ]
   └─ Invokes registered readers (Parquet, CSV, JSON, Arrow/Pandas pointers)
        │
        v
[ 3. Schema & Metadata Sampling ]
   └─ Inspects file headers/footers or memory pointers to infer column types
        │
        v
[ 4. Transient Catalog Injection ]
   └─ Generates temporary synthetic table entry for query plan duration

-- Direct execution over uningested S3 Parquet file using Replacement Scans
SELECT user_id, COUNT(*) AS event_count
FROM 's3://analytics-bucket/events.parquet'
WHERE event_type = 'conversion'
GROUP BY user_id;

Storage Layout & Memory Management

  • Single-File Database Persistence: Persistent DuckDB instances pack schemas, metadata, indexes, and compressed columnar data blocks into a single database file. DuckDB can also run entirely in-memory (:memory:).
  • Out-of-Core Execution Spilling: When query memory requirements (such as building massive join hash tables or global sorting buffers) exceed available physical RAM, DuckDB automatically spills working sets out-of-core to temporary disk files, enabling analytical queries over datasets larger than system memory.

Extension Ecosystem

To maintain a compact core binary ($\sim 30\text{ MB}$) free of heavy external dependencies (such as OpenSSL), DuckDB uses a dynamic C++ extension system: * Dynamic Loading: Extensions are downloaded on demand and dynamically linked into the running host process via SQL commands: sql INSTALL httpfs; LOAD httpfs; * Core Extensions Overview: * httpfs: Provides HTTPS and AWS S3/GCS object storage read/write capabilities (statically links OpenSSL). * json: Adds native JSON parsing, JSON pointer expressions, and raw file scanning operators. * spatial: Adds geospatial data types, ST spatial functions, and GDAL vector format integrations. * iceberg / delta: Provides direct read and scan support for Lakehouse transactional table formats. * postgres_scanner / sqlite_scanner: Executes parallel vector scans directly over external PostgreSQL or SQLite database files. * Extension Security & Trust Boundary: Loading an extension downloads compiled binary artifacts from external repositories and executes C++ logic directly within the host process memory space. This represents an explicit security and trust boundary.

6. Concurrency Models, Traps, & Failure Modes

Concurrency Comparison Matrix

DuckDB enforces structural concurrency rules governed strictly by its single-file buffer management and single-writer core architecture:

Operating Dimension Single-Process Native Engine Multi-Process Ecosystem Alternatives
Primary Architectural Paradigm In-Process Dual Mode: Single process read-write lock, or multi-process read-only access. Network / Catalog Proxy: External protocol proxy or centralized catalog transaction coordinator.
Write Execution Mechanics Single Process Multi-Threaded: One process attaches in Read-Write mode. Multiple concurrent writer threads execute via MVCC + Optimistic Concurrency Control (OCC). Client-Server Proxy (Quack / DuckLake):
• Quack Protocol: Exposes DuckDB over a client-server network protocol.
• DuckLake Format: Uses a central PostgreSQL catalog to coordinate multi-process transactions.
Read Execution Mechanics Multi-Process Shared Read: Unlimited distinct OS processes can attach simultaneously in Read-Only mode (access_mode = 'READ_ONLY'). Distributed Catalog Reads: Multiple engine instances read shared object storage segments coordinated via PostgreSQL catalog metadata locks.
Buffer Cache & Locking Strict exclusive OS file lock on .duckdb database file to protect in-memory buffer caches from corruption. Shared directory access routed through PostgreSQL catalog locks or proxy server connection pools.

Edge Cases, Traps, and Failure Modes

Trap / Anti-Pattern Symptom / Error Root Cause Mitigation / Corrective Action
Concurrent Cross-Process Writes IO Error: Could not set lock on file... or file lock initialization crashes. DuckDB places an exclusive OS lock on the database file to protect in-memory buffer caches from multi-process corruption. Open secondary processes in READ_ONLY mode, mount via the Quack remote protocol, or use DuckLake with a PostgreSQL catalog.
Database File Hosted on NAS / Shared SMB Mounts File lock failure crashes, IO Error, or silent buffer cache state corruption. Network Attached Storage (NAS) and cross-OS SMB mounts provide unreliable POSIX byte-range file locking and broken cache invalidation semantics. Host .duckdb files strictly on local NVMe/SSD storage, mount network directories as read-only, or transition to DuckLake format.
Simultaneous Row Edits / Mutations Transaction conflict: cannot update a table that has been altered! Optimistic Concurrency Control (OCC) aborts a transaction when two internal writer threads edit or delete the same row concurrently. Implement retry loop logic inside application code when intercepting transaction conflict exceptions.
Unconstrained Cartesian Joins Exponential memory blow-up or forced heavy disk spilling. Missing join keys or cross-product join logic generating runaway intermediate result cardinalities. Validate join equality predicates, evaluate query cardinality estimates using EXPLAIN, and enforce key constraints.
Host Language Type Conversions Unexpected schema cast failures, timezone offset shifts, or timestamp truncations. Misalignments between language type systems (e.g., Pandas nanosecond timestamps) and DuckDB strict SQL type definitions. Apply explicit SQL CAST expressions during replacement scans or inspect sampled schema types prior to query execution.
OLTP Multi-User Server Misuse Severe row-lock contention, high transaction abort rates, degraded point lookup throughput. Using DuckDB as a high-concurrency transactional web application database instead of an analytical query engine. Re-architect transactional point-update workloads to a dedicated OLTP engine like PostgreSQL or SQLite.
